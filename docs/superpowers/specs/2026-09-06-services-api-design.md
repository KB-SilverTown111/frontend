# 온보딩 제외 서비스 화면·API 연결 설계

## 목표

온보딩을 제외한 송금, 고지서, 생활금융, 공통 음성 화면을 현재 Figma·프로토타입의 화면 순서와 문구를 기준으로 production 라우트에 구현한다. 백엔드 코드는 변경하지 않고, 현재 API 계약에 맞는 프론트엔드 API 모듈·상태·화면 동작만 추가한다.

## 기준과 범위

- 화면 기준: Figma의 `송금6`, `고지서6`, `생활금융6`, `보이스6` 및 기존 프로토타입 데이터
- 계약 기준: Notion API 명세와 `API 계약 공통 규칙 — MVP`
- 제외: 이미 구현된 온보딩 화면·스토어의 동작 변경, 백엔드 소스/DB/배포 변경
- 인증: 기존 Axios 클라이언트와 저장된 액세스 토큰을 사용한다. 401은 기존 인증 흐름으로 돌아갈 수 있도록 공통 오류로 노출한다.
- 외부 연동: 서버가 제공하는 OCR·납부·MMS mock API를 호출하되, 프론트에서 외부 공급자 키를 다루지 않는다.

## 구현 방향

### 1. 도메인 API 모듈

HTTP 세부사항은 화면에서 분리하고, `src/api` 아래에 계약 단위 모듈을 둔다.

- `accounts`: `GET /accounts`
- `transfers`: 금액 검증, 수취인 후보, 초안 생성/조회/확인/PIN 인증/실행/취소, Risk Score·추가 확인, 보호자 인증
- `bills`: OCR multipart, 목록/월별 요약/상세, 확인, mock 납부 실행
- `reminders`: 목록/생성/수정/취소/미루기
- `mobileBranches`: 목록/상세
- `voice`: 세션 생성·조회·종료, 턴 처리, 이벤트(REPLAY/INTERRUPTED), Speech 단기 토큰, 음성 설정
- `profile`: 사용자 정보·동의 조회/수정

모든 모듈은 `apiClient`만 사용하고, 응답 DTO는 서버 필드명을 보존한 얇은 파서로 반환한다. 쓰기 API는 계약에 따라 `Idempotency-Key`를 생성하며, 음성 설정 PUT처럼 요청 자체 멱등인 API에는 키를 붙이지 않는다.

### 2. 공유 Pinia 상태

- `serviceData`: 계좌, 고지서, 리마인더, 이동점포의 조회 결과와 로딩/오류 상태
- `transfer`: 수취인·금액·출금계좌·transferId·Risk/보호자 인증·confirmation 상태를 보관하며 화면 단계만으로 실행하지 않는다.
- `bill`: 촬영/선택 이미지, OCR 후보, billId, 확인 토큰, 실행 결과를 보관한다. 이미지와 토큰은 메모리의 일시 상태로만 둔다.
- `voice`: sessionId, 서버 currentStep/status, 최신 tts/displayCard, STT 처리 상태를 보관한다.

스토어는 상태 전이와 요청 조합만 담당하고 HTTP 호출은 API 모듈에서 수행한다. 민감정보와 전체 연락처/음성 원문은 로그에 남기지 않는다.

### 3. 화면 연결

기존 production 라우트 ID를 유지하고, `ServiceRouteView`에 API-backed 화면용 동작 슬롯을 제공한다. 프로토타입 컴포넌트를 재사용하지 않고, 프로토타입의 문구·상태를 production 화면의 초기/빈 상태 표현에만 사용한다.

- 송금: 계좌·수취인 조회 → 금액 검증 → prepare → read-back/confirm → Risk·보호자 확인 → PIN 인증 → execute → 완료/실패
- 고지서: 카메라/파일 선택 → OCR → 후보 재확인 → confirm → mock execute → 완료/실패. Capacitor 카메라 권한은 촬영 시점에 요청한다.
- 생활금융: 계좌 목록, 리마인더 CRUD, 위치 기반 이동점포 목록/상세, 사용자/동의/음성 설정 화면을 API 응답으로 채운다. 위치 거부 시 지역 직접 선택을 유지한다.
- 공통 음성: entryPoint별 세션 생성, 서버 currentStep 복원, STT 턴·REPLAY/INTERRUPTED 이벤트, 종료, Speech 토큰 요청을 연결한다. 서버 장애 시 텍스트 대체 상태를 보여준다.

API 응답이 없는 개발 환경에서는 화면이 깨지지 않도록 로딩·빈 목록·오류 상태를 명시하고, 임의의 금융 실행 성공을 표시하지 않는다.

### 4. 접근성·안전

- 큰 글씨와 충분한 터치 영역을 유지하고, 상태는 색상과 텍스트/아이콘을 함께 표시한다.
- 송금·납부는 서버 응답의 상태와 토큰이 모두 준비된 경우에만 다음 실행 동작을 활성화한다.
- 계좌번호·주민번호·전화번호·토큰·PIN은 화면/로그에서 마스킹한다.
- 권한 거부·세션 만료·멱등성 충돌·네트워크 오류를 사용자용 짧은 메시지로 변환한다.

## 검증 계획

1. 도메인 API 모듈의 HTTP 메서드·경로·본문·멱등성 헤더 단위 테스트
2. 핵심 라우트 전환과 상태별 버튼 활성화 테스트
3. `npm run lint`, `npm run format:check`, `npm run build`
4. Capacitor Android에는 웹 자산을 동기화하고, 실제 권한/카메라 동작은 기기에서 수동 확인

## 완료 기준

- 온보딩 외 production 라우트가 모두 기존 Figma/프로토타입 화면 순서를 유지한다.
- 명세에 있는 프론트 사용 API가 도메인 모듈로 연결되고, 화면은 성공·빈 상태·오류 상태를 구분한다.
- 금융 실행은 확인 토큰·서버 상태·멱등성 규칙을 벗어나지 않는다.
- 백엔드 파일에는 변경이 없고, 온보딩 동작 회귀가 없다.
